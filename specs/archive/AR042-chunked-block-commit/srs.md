| 字段 | 内容 |
|------|------|
| AR 编号 | AR042 |

| 关联 SR | SR-042（质量-延迟权衡，承接 AR040/AR041） |
| 日期 | 2026-10-25 |

## 1. 背景

- AR040：整块一次性贪心提交在部分 prompt 上明显劣于官方迭代（p3：−1.537 vs −0.809）。
- AR041：把低置信块整块回退到官方迭代可**完全恢复质量**（logp 逐位相同），但速度掉到 1.4–1.5×。
- 两端之间的中间地带从未测量：**块内只迭代有限次**是否能拿到「接近官方的质量 + 远高于官方的速度」。

## 2. 机制

`FastDLLMSamplerConfig.commit_chunk_size`（默认 `0` = 关闭，行为与 AR041 末态逐字节一致）。
`>0` 时启用**块内渐进解掩**：

```
loop over rounds:
    logits = 当前块的决策行（首轮可复用 CDF 草稿 stash，否则前向一次）
    p = softmax(logits)[仍掩码位, 该位贪心 token]
    取 p 最大的 chunk 个位置填入贪心 token
    若仍有掩码 -> 前向该块（历史 KV 作前缀），进入下一轮
```

每块前向数 ≈ `ceil(掩码数 / chunk)`。`chunk=32` 退化为一次性提交（≈D），
`chunk=1` 逼近官方逐位置解掩（但采用贪心而非 0.95 阈值）。

## 3. 目标（冻结判定）

在 AR040 的 3 条 prompt × 160 token 上，与已有 A（官方）与 D（一次性）数字对比：

- **H1 单调性**：`chunk` 越小，mean log p 越高（越接近 A）——至少 2/3 prompt 满足单调不减；
- **H2 覆盖**：存在某个 `chunk` 使 `logp >= logp(A) - 0.05`（即达到「质量平价」）；
- **H3 成本**：该 `chunk` 的墙钟仍显著低于 A（≥2×），且每块前向数 == `ceil(掩码数/chunk)`（账本可核）；
- **H4 复现**：双跑逐位一致。

任一失败 → 如实记录（若 H2 不成立，说明贪心渐进也无法替代官方阈值规则）。

## 4. 功能需求

### F1 渐进解掩

**验收标准**：
- Given `commit_chunk_size=0`，Then 与 AR041 末态逐字节一致；
- Given `chunk=k>0`，Then 每轮恰好填 `min(k, 剩余掩码数)` 个**置信度最高**的掩码位；
- Given 块内掩码全部填完，Then 退出并返回「完成」，不再发起验证。

### F2 与 CDF 组合

**验收标准**：Given 存在草稿 stash，Then 首轮不额外前向（stash 复用），账本 `spec_chunk_forwards` 只计后续轮。

### F3 账本

**描述**：`history_cache_stats` 新增 `spec_chunk_forwards`（默认关为 0）。

## 5. 非功能需求

| 类型 | 指标 | 要求 |
|------|------|------|
| 质量 | 平价 | 存在 chunk 使 logp ≥ A − 0.05 |
| 性能 | 加速 | 平价点的加速 ≥ 2× |
| 兼容 | 默认关 | 与 AR041 末态逐字节一致 |
| 可靠性 | 一致性 | 每块前向数可预测、可核对 |

## 6. 约束与假设

- 真实 checkpoint、无 mock、`stop_token_id=-1`、160 token；
- 假设 A1：块内双向注意力使「先填高置信位」能改善后续位置（这是机制成立的前提，由 H1 检验）；
- 假设 A2：贪心渐进可近似官方阈值规则的质量（由 H2 检验，可能被证伪）。

## 7. 术语

| 术语 | 定义 |
|------|------|
| chunk | 每轮填充的掩码位数 |
| 渐进解掩 | 块内多轮「填最高置信的 chunk 个 → 重新前向」 |
| 平价点 | logp 与官方解码差距 ≤ 0.05 的 chunk 取值 |
